2. Runtime watch multi-fingerprint design
- Phase28 keeps correctness lifecycle unchanged and adds a stronger operator layer on top of the existing runtime lifecycle.
- Same-fingerprint runtime watch remains the source for `WATCH_STABLE` vs `CLEAR` operator decisions.
- Multi-fingerprint runtime matrix is kept separate and intentionally stress-tests comparability boundaries:
  - `exact_current`
  - `same_host_compiler_bump`
  - `sanitizer_change`
  - `runner_tag_change`
  - `cross_host`
  - `retired_only`
- Phase28 hardens runtime lineage handling so runtime history/watch buckets are keyed only by `runtime_fingerprint_key`; host/toolchain similarity no longer collapses changed execution signatures into one bucket.
- Pipeline defaults now resolve runtime registry/proposal paths even when the caller omits them, and `--pipeline-phase` defaults to auto inference instead of pinning every run to `phase28`.

12. Remaining risks
- runtime watch evidence is still strongest on the current Apple clang 17 / arm64 lineage; more real hosts and toolchains would make the registry/history less synthetic.
- `asan_full` remains soft-over-budget. Phase28 shows it is stable and bounded, not a correctness drift, but further repeated evidence may still justify a future runtime rebaseline proposal.
- runtime history currently contains legacy single-fingerprint samples from earlier phases. Phase28 stops future bucket collapse, but older history is not retroactively repartitioned.
- because phase28 now distinguishes same-fingerprint watch from multi-fingerprint comparability, operators must read `policy_pipeline_quick_phase28.json` and `policy_pipeline_matrix_phase28.json` together instead of treating one summary as universal.
