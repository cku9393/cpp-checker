# Failure Analysis Playbook

This file is an auxiliary analysis target for the branch_3 retry loop.

Purpose:
- Force each post-failure analysis mini-session to leave behind a concrete refinement to the analysis process.
- Keep the next solver retry anchored to narrower failure localization than the previous attempt.

Mandatory refinement rule:
- After each failed solver workflow, the analysis-only mini-session must update either this playbook or `.ouroboros/capture_failure_context.py` before the next solver retry is allowed to start.

Retry-gate freshness rule:
- Before any solver retry resumes, `.ouroboros/failure_analysis_state.json` must be present and explicitly marked current for the latest captured failure with a matching attempt/session/timestamp/signature tuple taken from the newest failure report and breakdown.
- Treat a mere mtime bump as insufficient. If the refreshed state cannot prove it is tied to the newest captured failure, the retry loop must stop instead of starting another blind solver retry.
- Every refreshed `.ouroboros/failure_analysis_state.json` and `.ouroboros/failure_analysis_iteration.md` must also record explicit post-failure freshness evidence: latest failure report timestamp, latest failure breakdown timestamp, the analysis refresh timestamp, and a yes/no verdict that the refresh happened after the current failure. Do not rely on filesystem mtime alone.
- A qualifying post-failure refresh now means at least one branch-local analysis asset changed after the latest failure baseline, not just the retry gate itself. Treat `.ouroboros/capture_failure_context.py`, `.ouroboros/failure_analysis_playbook.md`, `.ouroboros/failure_analysis_iteration.md`, `.ouroboros/failure_analysis_state.json`, `.ouroboros/refresh_analysis_state.py`, and similar diagnosis-tightening helpers as qualifying. Do not let `.ouroboros/verify_analysis_refresh.py` satisfy the gate by itself.
- The state file alone no longer satisfies that retry gate. `refresh_evidence.qualifying_refreshed_assets` must include at least one supporting analysis helper or note besides `.ouroboros/failure_analysis_state.json`. The preflight should block if the state evidence is empty/self-only, and it must not treat a freshly rewritten `latest_analysis_session.md` as a substitute unless that note is itself recorded in state freshness evidence.
- Treat "supporting analysis asset" literally: when retry start is gated by `--require-current-state`, every qualifying supporting asset and `refresh_evidence.freshness_record.refreshed_asset` must resolve under the branch-local `.ouroboros/` analysis root. Do not let `artifacts/.../latest_analysis_session.md`, retry-report republishes, or other non-branch-local files satisfy the freshness proof.
- Persist a singular freshness record alongside that asset list. `refresh_evidence.freshness_record` must name one supporting refreshed helper or note, and it must repeat the latest failure attempt/session/timestamp/signature tuple so the next solver session can see exactly which asset satisfied freshness without inferring it from an unordered list.
- The freshness record is the gate, not just an annotation. Before another solver retry starts, `refresh_evidence.freshness_record.refreshed_asset` itself must be newer than the newest failure timestamp. The preflight must not accept a different supporting asset as the real freshness proof while the recorded asset stays stale.
- Keep the shared verifier aligned with that rule. When `--require-current-state` is active, `verify_analysis_refresh.py` must also reject baseline/post-failure freshness that comes only from `.ouroboros/failure_analysis_state.json`; at least one supporting helper or note must be newer than the baseline and the latest failure timestamp.
- The retry gate must compare qualifying analysis-asset freshness against the latest captured failure itself, not only against the analysis-round start time. Use the newest timestamp among the latest failure report, latest failure breakdown, and current-failure state markers as the minimum freshness floor for at least one qualifying analysis asset.
- The retry gate must verify both halves together before another solver retry starts: the singular `freshness_record.refreshed_asset` must be a supporting qualifying analysis asset refreshed after baseline and after the newest failure timestamp, and `.ouroboros/failure_analysis_state.json` must still prove `refresh_evidence` timestamps plus post-report/post-breakdown booleans for the newest captured failure.
- Keep `artifacts/lca_tree_stress_v5/retry_loop/latest_analysis_session.md` as a credibility summary, not as the branch-local freshness proof. Launcher-side retry entrypoints may block a stale carry-forward session summary before the loop starts, but the shared `.ouroboros` preflight still needs its own refreshed branch-local analysis asset even when that summary exists.

Formal-closure credibility rule:
- Treat `AC 4`, `AC 5`, and `AC 6` PASS labels as invalid unless the artifact body contains fresh same-worktree rerun evidence for the required gates, not merely a narrative about future reruns or a carried-forward PASS from older artifacts.
- When the solver still shows real progress on the pinned axis but those fresh rerun artifacts do not exist, record the outcome as partial progress or a guard-rejected nominal PASS. Do not let report wording overstate formal closure.
- Keep this rule active even when `AC 5` remains the primary pinned optimization target. Solver-side progress and report honesty are co-requirements, not sequential phases.

Pinned AC subset narrowing rule:
- When repeated same-worktree failures keep landing on the same upstream AC and the downstream ACs are only blocked or guard-rejected for missing reruns, refresh `.ouroboros/failure_analysis_state.json` with an explicit AC-subset decision rather than leaving the next retry to infer it from the workflow summary.
- Store the surviving pinned retry subset, the broader rendered baseline that was narrowed away, and one exclusion reason per dropped AC. This prevents the next solver session from silently re-expanding AC4/AC5/AC6/AC7/AC8 after an AC3-only repeat failure.

Refinement ladder:
1. Identify the failed AC and blocked downstream ACs from the last workflow.
2. Map the failure to dominant execution phases.
3. Narrow the issue from file-level to symbol-level.
4. Narrow the issue from symbol-level to line-range and code-excerpt evidence.
5. If repeated failures still hit the same file/symbol/range, add a sharper analysis rule so the next capture distinguishes subcases instead of repeating the same broad diagnosis.
